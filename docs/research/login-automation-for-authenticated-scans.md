# Drive the real login, then prove it worked

Security scanners, synthetic monitors, test frameworks and the better accessibility scanners all get automated runs past a login with the same ladder. The bottom rung is a real browser that signs in from nothing more than a URL, a username and a password. If that fails, the next rung is a short list of declarative steps, then a recorder or a saved browser session, and finally a script hook. **MFA is automated in exactly one way**: a base32 TOTP seed with SHA1, 30-second and 6-digit defaults, which ZAP, Burp, GitLab, Invicti, Datadog, mabl and Escape all ship. For push, SMS and CAPTCHA, every vendor tells users to exempt a dedicated test account. The identity providers agree. Auth0 says integration tests "do not need to pass MFA challenges", Microsoft says to automate only in a separate test tenant, and both are retiring the password-grant shortcuts testers used to rely on. Hosted logins such as Auth0 Universal Login are **state machines with roughly 28 documented prompt types** whose CSS classes change on every build. The tools that cope with them run a "recognise the screen, then act" loop with provider-specific knowledge rather than a fixed script; ZAP spent about a year of releases on Microsoft's login alone. No tool documents capturing a token held only in page memory. The robust answer is to run the login in the same browser that does the scanning, which a11ign already does. The most useful hard data comes from ZAP's daily tests: **its zero-config login found the username and password fields on every target, yet 8 of 21 runs still failed**, almost all at confirming the login had worked or at popups. a11ign should therefore make its default a `login:` block of credentials, an optional TOTP seed and a signed-in check, run by an Auth0-aware screen loop. Flows should stay as the override and gain optional and conditional steps, and `--auth-state` should be widened to carry identity-provider cookies and sessionStorage. The first engineering effort belongs on verification, failure artifacts and lockout guards, not on a recorder.

## Every tool category climbs the same four-rung login ladder

The tool categories arrived at this shape independently. **ZAP now calls Browser Based Authentication "often the most effective option, especially for modern apps"**, needs only `loginPageUrl` to run it, and says of its older form, JSON and script methods "We do NOT recommend using these options going forwards!" It describes its optional step list as "a half-way house to full scripting" ([ZAP: Authentication methods](https://www.zaproxy.org/docs/getting-further/authentication/authentication-methods/); [ZAP blog 2025-07-03](https://www.zaproxy.org/blog/2025-07-03-authentication-improvements/)). Invicti, Acunetix and Rapid7 ship the same zero-config tier, labelled "Simple form", "Try to auto-login into the site" and "Automated Login" ([Invicti: Simple form](https://docs.invicti.com/ip/simple-form-authentication); [Acunetix: OTP](https://www.acunetix.com/support/docs/configuring-form-authentication-with-otp/); [Rapid7](https://docs.rapid7.com/insightappsec/authentication/)). Escape's `browser_agent` preset takes only `login_url`, `username` and `password` ([Escape blog 2025-06-30](https://escape.tech/blog/more-support-for-complex-authentication-flows-totp-mfa-and-text-based-captcha/)).

PortSwigger is the outlier. Burp's "login credentials" mode is explicitly single-step, and PortSwigger recommends "using a recorded login sequence, even for sites that use basic username and password authentication". It now lets Burp AI do the recording from the same three fields, but in Burp DAST that option exists only on Cloud instances, and it cannot handle MFA ([Burp: Login credentials](https://portswigger.net/burp/documentation/scanner/authenticated-scanning/login-credentials); [Burp DAST: Using recorded logins](https://portswigger.net/burp/documentation/dast/user-guide/scanning-web-apps/configure-authentication/recorded-logins)). At the top of the ladder, StackHawk's `externalCommand` runs any process that prints `{"headers":[…],"cookies":[…]}` to stdout ([StackHawk: External Command](https://docs.stackhawk.com/hawkscan/authenticated-scanning/external-command-authentication/)). GitLab DAST has no zero-config rung at all. It requires `DAST_AUTH_USERNAME_FIELD`, `DAST_AUTH_PASSWORD_FIELD` and `DAST_AUTH_SUBMIT_FIELD` selectors ([GitLab DAST authentication](https://docs.gitlab.com/user/application_security/dast/browser/configuration/authentication/)).

Monitoring and test-automation tools lean on recording and saved sessions. Datadog runs the recorded login at the start of every browser test and packages it as a reusable subtest ([Datadog: App that requires login](https://docs.datadoghq.com/synthetics/guide/app-that-requires-login/)). Ghost Inspector imports an "Import Only" login test into other tests ([Ghost Inspector: Modules](https://docs.ghostinspector.com/getting-started/logging-in-with-modules/)). mabl offers a zero-config auto-login but documents that it fails "if the login requires more than username and password or if the login isn't in English"; this comes from a search excerpt, because mabl's help centre blocked direct fetches ([mabl: Auto-login flows](https://help.mabl.com/hc/en-us/articles/19078187773972-Auto-login-flows)). Playwright's documented pattern is a setup project that logs in once and saves `storageState` for every test. Cypress caches a login per spec with `cy.session` and drives identity-provider pages with `cy.origin` ([Playwright: Authentication](https://playwright.dev/docs/auth); [Cypress: cy.session](https://docs.cypress.io/api/commands/session)).

Accessibility scanners sit lowest on the ladder. At least six vendors (Level Access, Pope Tech, Evinced, UserWay, Acquia and BrowserStack) ask for the same single-form fields. Those fields are a login URL, the username and its CSS selector, the password and its selector, a submit selector, and usually a success selector ([Level Access: Secure web authentication](https://client.levelaccess.com/hc/en-us/articles/5324907203863-Set-up-secure-web-authentication); [Pope Tech](https://app.pope.tech/help-center/article/configure-website-authentication)). Their step vocabularies come down to type, click, select, wait for a selector, wait for a URL, and navigate. That holds for Pope Tech's advanced steps, UserWay's Scenario commands, Pa11y's `actions` and Deque's axe CLI spec files ([UserWay Scenario](https://help.userway.org/en/articles/6469789-introduction-to-building-custom-scenario-scans-in-userway-s-accessibility-monitor); [pa11y README](https://github.com/pa11y/pa11y); [axe DevTools CLI](https://docs.deque.com/devtools-for-web/4/en/cli-workflow-specs/)).

Anything harder goes to vendor staff. Adding credentials in Siteimprove "creates a support ticket" so Siteimprove can write an authentication script ([Siteimprove: Adding credentials](https://help.siteimprove.com/support/solutions/articles/80001089185-adding-and-replacing-credentials-for-non-public-sites)). Silktide's custom authentication "may incur additional costs" ([Silktide](https://help.silktide.com/en/articles/8012756-can-silktide-test-password-protected-websites)). TPGi's ARC team records a Selenium script "for an extra fee" ([tpgarc.com](https://www.tpgarc.com/)).

The other accessibility route is in-suite. Deque's axe Watcher, Evinced's SDKs and Siteimprove's Alfa Code Checker run inside the customer's Playwright, Cypress or Selenium tests and inherit whatever login those tests already do. Deque documents Playwright `storageState` together with the `mergeTests` step needed to combine its fixtures with the customer's auth fixture ([axe Watcher: storageState](https://docs.deque.com/devtools-for-web/4/en/wa-storagestate/); [Evinced SDKs](https://evinced.com/products/auto-test-sdks)).

| Rung | Security scanners | Monitoring and test frameworks | Accessibility scanners |
|---|---|---|---|
| URL and credentials; the tool finds the fields | ZAP Browser Based Auth, Invicti simple form, Rapid7 Automated Login, Escape `browser_agent`, Burp AI recording | mabl auto-login (English, two fields only) | None documented without selectors |
| Declarative steps or selectors | ZAP auth steps, GitLab `DAST_AUTH_*`, Bright stages | Datadog steps with optional flags | Level Access, Pope Tech, Evinced, UserWay, Acquia and BrowserStack forms; Pa11y `actions`; axe CLI specs |
| Recorder or saved session | Burp Login Recorder, Invicti LSR, Rapid7 macro, Detectify, Snyk | Datadog, mabl and Ghost Inspector recorders; Playwright `storageState`; `cy.session` | Level Access Chrome Recorder import and Desktop Crawler App; Deque `storageState` |
| Script or command | StackHawk `externalCommand`, ZAP scripts, Invicti script actions | Checkly and New Relic scripts | LHCI `puppeteerScript`, UserWay Scenario JS, scripts written by vendor staff |

No vendor publishes which rung its customers actually use. **The only public success data is ZAP's daily authentication test table.** Given only the login URL and credentials, ZAP's browser login passed **13 of 21 targets (about 62%)**. It passed 4 of 5 with some extra configuration, and 1 of 1 with a recorded client script. In every row, including the failures, ZAP found the username and password fields. Five of the eight failures came from not detecting whether the login had succeeded, one from not identifying the session, and one from popups (instagram.com). The cause of the reddit.com failure is not given ([ZAP Authentication Tests](https://www.zaproxy.org/docs/scans/auth/)). The sample is small, partly synthetic and changes daily. Still, it points one way: **finding the fields is a solved problem, and the remaining work is knowing whether the login worked and getting past interstitial screens**.

## Hosted sign-in pages are state machines that defeat fixed scripts

**Auth0's New Universal Login documents about 28 prompts, each with one or more screens.** Which ones a test user meets depends on tenant settings, not on the app ([Auth0: Customize text elements](https://auth0.com/docs/customize/login-pages/universal-login/customize-text-elements)).

With correct credentials, the same user can meet many different paths. "Identifier First" adds a separate password screen, or redirects to an enterprise IdP when the email domain matches, while "Identifier + Password" puts both fields on one screen ([Auth0: Identifier First](https://auth0.com/docs/authenticate/login/auth0-universal-login/identifier-first)). Passkey "Progressive Enrollment" is **checked by default** on database connections. It prompts users to create a passkey after login, and they can defer it every 30 days ([Auth0: Passkey policy](https://auth0.com/docs/authenticate/database-connections/passkeys/configure-passkey-policy)). The MFA policy can be "Never", "Use Adaptive MFA" or "Always", and post-login Actions can add a "Try Another Method" option or a factor picker, or force enrollment ([Auth0: Enable MFA](https://auth0.com/docs/secure/multi-factor-authentication/enable-mfa); [Auth0: Customize MFA selection](https://auth0.com/docs/secure/multi-factor-authentication/customize-mfa/customize-mfa-selection-universal-login)). Bot Detection set to "When Risky" inserts an `interstitial-captcha` screen on some runs only ([Auth0: Bot Detection](https://auth0.com/docs/secure/attack-protection/bot-detection)). First-party apps can skip consent, but "a login confirmation prompt may still appear when the application uses a non-verifiable callback URI (such as `localhost`…)" ([Auth0: User consent](https://auth0.com/docs/get-started/applications/confidential-and-public-applications/user-consent-and-third-party-applications)). Organizations can add an organization picker before or after credentials ([Auth0: Organizations login flows](https://auth0.com/docs/manage-users/organizations/login-flows-for-organizations), search excerpt).

The markup is not a stable contract either. Auth0 warns that "CSS class names change each time Auth0 builds the project" and that "The HTML structure of Universal Login pages is subject to change" ([Auth0: Customize page templates](https://auth0.com/docs/customize/login-pages/universal-login/customize-templates)). Auth0's own December 2024 Cypress article anchors on `input#username`, `input#password` and a "Continue" button, but no document guarantees them ([Auth0 blog: Testing Auth0 login with Cypress](https://auth0.com/blog/testing-auth0-login-with-cypress/)). The markup also changed recently. The opt-in toggle for Auth0's WCAG 2.2 AA-compliant Universal Login UI reached end of life in July 2025, retiring the older, non-accessible UI ([Auth0: Deprecations](https://auth0.com/docs/troubleshoot/product-lifecycle/deprecations-and-migrations)). Tenants on Advanced Customizations (ACUL) replace the UI screen by screen with their own React or vanilla JS ([Auth0: ACUL](https://auth0.com/docs/customize/login-pages/advanced-customizations)). Okta's Gen3 widget likewise "doesn't use fixed CSS class names" ([Okta: Gen3 migration](https://developer.okta.com/docs/guides/custom-widget-migration-gen3/main/)).

The other providers add their own interstitials. Microsoft Entra shows "Stay signed in?" after a successful sign-in, and abandoning it logs error 50140 ([Microsoft Learn: Stay signed in](https://learn.microsoft.com/en-us/entra/fundamentals/how-to-manage-stay-signed-in-prompt)). Entra registration campaigns offer "Skip for now". With limited snoozes, the user can skip three times before registration becomes mandatory, and the Authenticator nudge does not appear after a TOTP sign-in ([Microsoft Learn: Registration campaign](https://learn.microsoft.com/en-us/entra/identity/authentication/how-to-mfa-registration-campaign)). Okta goes identifier-first when its session policy allows any factor. On later sign-ins in the same browser it shows "a full list of available authenticators", and it prompts for optional authenticators with a way to continue without enrolling ([Okta: Identifier-first](https://developer.okta.com/docs/concepts/oie-idfirst-signin/); [Okta: End-user sign-in](https://help.okta.com/oie/en-us/content/topics/identity-engine/policies/about-sign-in-process.htm); [Okta: Enrollment policies](https://help.okta.com/oie/en-us/content/topics/identity-engine/policies/about-mfa-enrollment-policies.htm)). Cognito managed login returns "Something went wrong" on any prompt not completed within five minutes ([AWS: Managed login](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-managed-login.html)).

Tools cope in three ways. The first is to follow the identity provider off the app's origin. Burp "can temporarily follow any out-of-scope links that are necessary to perform the login sequence", provided the sequence ends on an in-scope page ([Burp: Recorded login sequences](https://portswigger.net/burp/documentation/scanner/authenticated-scanning/recorded-login-sequences)). The second is to add a selector for the second page. GitLab handles two-page logins with `DAST_AUTH_FIRST_SUBMIT_FIELD` plus before- and after-login click paths, though it admits it "cannot authenticate to applications that require more text inputs than username, password, and optional TOTP" ([GitLab DAST](https://docs.gitlab.com/user/application_security/dast/browser/configuration/authentication/)). Level Access's optional "username submit button selector" does the same job for "two page authentication" ([Level Access](https://client.levelaccess.com/hc/en-us/articles/5324907203863-Set-up-secure-web-authentication)). The third is to build heuristics. ZAP looks for fields "across single or multiple pages", inside shadow DOMs, and behind login links it has to discover ([ZAP: Browser Based Authentication](https://www.zaproxy.org/docs/desktop/addons/authentication-helper/browser-auth/); [ZAP authhelper changelog](https://www.zaproxy.org/docs/addons/authhelper/changelog/)).

**ZAP's changelog is the clearest evidence of what supporting one hosted provider costs.** Microsoft-login support landed in mid-2025. December 2025 added account selection, the TOTP step, and a rule to "Fail the Microsoft login if not able to perform all the expected steps". March 2026 added logins in a popup window, May 2026 improved detection of when the login has finished, and June 2026 handled the "Permissions requested" consent screen ([ZAP authhelper changelog](https://www.zaproxy.org/docs/addons/authhelper/changelog/)). That is roughly a year of work for one provider. No Auth0- or Okta-specific handling appears in ZAP or in any other vendor's docs that were read.

For screens that appear only sometimes, recorder tools fall back to blunter instruments. Datadog marks a step "If this step fails, continue to next step", which costs up to the step timeout (60 seconds by default) every time the screen is absent ([Datadog: Advanced options](https://docs.datadoghq.com/synthetics/browser_tests/advanced_options/)). Playwright's `page.addLocatorHandler` (v1.42) checks for a registered overlay before every action; its own example is a "Confirm your security details" page ([Playwright: addLocatorHandler](https://playwright.dev/docs/api/class-page#page-add-locator-handler)). Cypress argues the opposite: "you cannot do conditional testing safely if you want your tests to run 100% consistently", so control the state in advance instead ([Cypress: Conditional testing](https://docs.cypress.io/app/guides/conditional-testing)). For a scanner pointed at other people's tenants, both positions are right. Skippable nudges that the adopter cannot or will not turn off need runtime handling. Everything else should be settled in the tenant, with the tool failing fast when it isn't.

## Memory-only tokens survive only in the browser that logged in

The default Auth0 SPA SDK keeps tokens in page memory, which Auth0 says "does not persist across page refreshes or browser tabs". On reload the SDK restores the session from one of two sources. One is a hidden iframe with `prompt=none`, which "will not work in browsers that block third-party cookies". The other is rotating refresh tokens. Apps can opt into `cacheLocation: 'localstorage'` instead, which Auth0 warns exposes the tokens to XSS ([Auth0: SPA SDK](https://auth0.com/docs/libraries/auth0-single-page-app-sdk)).

**No tool in this research documents capturing a token that lives only in JavaScript memory.** The nearest mechanisms all intercept or copy something the browser exposes. ZAP takes the session from the first post-login response that contains an `Authorization` header or JSON fields named `AccessToken` or `token` ([ZAP: Browser Based Authentication](https://www.zaproxy.org/docs/desktop/addons/authentication-helper/browser-auth/)). Invicti intercepts "AJAX-based bearer tokens" ([Invicti Enterprise](https://docs.invicti.com/ie-is/form-authentication-configure-verify)). GitLab treats sufficiently random cookie, localStorage and sessionStorage values as tokens, and admits it "cannot authenticate to applications that do not set an authentication token during login" ([GitLab DAST](https://docs.gitlab.com/user/application_security/dast/browser/configuration/authentication/)). Escape extracts cookies, localStorage and sessionStorage ([Escape blog 2025-03-21](https://escape.tech/blog/complex-authentication-in-dast-scans/)). Playwright's `storageState` covers cookies, localStorage, IndexedDB (since v1.51), origin private file system data and virtual passkeys, but "Playwright does not provide API to persist session storage" ([Playwright BrowserContext API](https://playwright.dev/docs/api/class-browsercontext); [Playwright: Authentication](https://playwright.dev/docs/auth)). Cypress's `cy.session` does include sessionStorage, but only within a run ([Cypress: cy.session](https://docs.cypress.io/api/commands/session)).

Saved state is fragile even when it captures the right storage. Playwright tells users to "delete the stored state when it expires", and its issue tracker shows the same failures again and again. One reporter's state was "only valid for a few hours" ([#9613](https://github.com/microsoft/playwright/issues/9613)). In an Auth0-plus-MFA thread, refresh-token rotation invalidated the saved file, and setup ran in a different browser from the tests ([#32594](https://github.com/microsoft/playwright/issues/32594)). Another user's state worked locally but not in GitHub Actions ([#32302](https://github.com/microsoft/playwright/issues/32302)). A maintainer's answer to stale tokens was that "you have to re-login" ([#16627](https://github.com/microsoft/playwright/issues/16627)).

Monitoring vendors avoid all of this by **logging in fresh on every run**. Datadog's browser test "systematically executes the first login steps", and mabl reuses a session only within one plan run ([Datadog](https://docs.datadoghq.com/synthetics/guide/app-that-requires-login/); [mabl: Logging into your app](https://help.mabl.com/hc/en-us/articles/19078165772564-Logging-into-your-app), search excerpt). Accessibility runners show what happens when the context is reset between pages. Under pa11y-ci's default `useIncognitoBrowserContext: true`, "a login performed while testing one URL does not carry over to another". Lighthouse CI keeps cookie auth across URLs but wipes localStorage auth unless `disableStorageReset` is set ([pa11y-ci](https://github.com/pa11y/pa11y-ci); [LHCI configuration](https://github.com/GoogleChrome/lighthouse-ci/blob/main/docs/configuration.md)).

Cypress's Auth0 guide also settles whether programmatic login is worth building. Logging in through the real UI with `cy.origin` needs "no further changes to your app", while the programmatic token path needs "an app appropriately built or adapted to use Auth0" ([Cypress: Auth0](https://docs.cypress.io/app/guides/authentication-testing/auth0-authentication)). For a scanner pointed at arbitrary apps, that rules out token injection as a general strategy.

These findings put a11ign's existing design in a better light than its feature list suggests. **A login that round-trips through the identity provider in the same browser, with that browser kept open for the scan, is the only documented-safe way to keep a memory-only token.** The weak spot is the other path. `--auth-state` carries only the run's own origin, so it lacks the identity-provider session cookie that silent re-authentication needs, and it inherits every expiry and rotation failure above. The same-browser path has one undocumented risk of its own. Each hard navigation to a new scan URL forces the SPA's SDK through its restore path. In-memory state should survive in-app navigation but not a reload, and no vendor documents how this plays out for scanners. A signed-in check after every navigation is therefore essential, not optional.

## TOTP seeds are the only unattended MFA, and providers prefer that tests skip MFA

The TOTP field set has become an industry standard. ZAP has had `users[].credentials.totp` with `secret`, `period`, `digits` and `algorithm`, plus a `TOTP_FIELD` step, since March 2025 ([ZAP AF environment](https://www.zaproxy.org/docs/desktop/addons/automation-framework/environment/); [ZAP changelog](https://www.zaproxy.org/docs/addons/authhelper/changelog/)). Burp DAST added TOTP in 2026.3 (April 2026), with fields for **TOTP secret**, **Algorithm**, **Period** and **Digits**, QR-code upload, and throttling of logins "to prevent TOTP code reuse before the passcode refreshes" ([Burp DAST: TOTP](https://portswigger.net/burp/documentation/dast/user-guide/scanning-web-apps/configure-authentication/totp-mfa); [DAST 2026.3](https://portswigger.net/burp/releases/dast-2026-3)). GitLab takes `DAST_AUTH_OTP_KEY` in Base32 and accepts only SHA-1, 30 seconds and 6 digits ([GitLab DAST](https://docs.gitlab.com/user/application_security/dast/browser/configuration/authentication/)). Datadog's "MFA Token" variable takes a secret key or a QR image and supports only SHA1 ([Datadog: TOTP](https://docs.datadoghq.com/synthetics/guide/browser-tests-totp/); [Datadog settings](https://docs.datadoghq.com/synthetics/settings/)). mabl made authenticator TOTP generally available in March 2024 ([mabl release note](https://help.mabl.com/hc/en-us/articles/23894445803028-2024-03-11-General-availability-of-MFA-authenticator-support)). QA.tech takes the whole `otpauth://` URI ([QA.tech: Handle auth](https://docs.qa.tech/best-practices/handle-auth)). Checkly and New Relic generate the code in script with the `otpauth` package. New Relic says to send the code straight to the field "instead of storing this in a variable", because the code is time-based ([Checkly](https://www.checklyhq.com/docs/learn/playwright/bypass-totp/); [New Relic 2FAOrMFA](https://github.com/newrelic/quickstarts-synthetics-library/blob/main/library/2FAOrMFA/config.yml)).

**No accessibility scanner found supports TOTP.** Pope Tech, TPGi ARC and Silktide say MFA is unsupported. Siteimprove allows only that TOTP "might be technically feasible", and BrowserStack's MFA add-on handles email OTP only ([Pope Tech](https://app.pope.tech/help-center/article/configure-website-authentication); [Siteimprove: MFA](https://help.siteimprove.com/support/solutions/articles/80001215842-can-siteimprove-crawl-through-mfa-logins-); [BrowserStack](https://www.browserstack.com/docs/website-scanner/scan-settings/general/test-pages-behind-login)).

Factors other than TOTP need extra infrastructure or a person. Snyk API & Web gives each target a webhook URL that the user posts emailed or texted codes to, and its docs suggest Google Apps Script or Power Automate to forward them ([Snyk: 2FA](https://docs.snyk.io/scan-fix-and-prevent/scan-with-snyk/snyk-api-web/configure-targets/configure-authentication/configure-two-factor-authentication)). Datadog gives each run its own email inbox ([Datadog: Test steps](https://docs.datadoghq.com/synthetics/browser_tests/test_steps/)). Rapid7 pauses a scan at "Awaiting Authentication" for a human, yet calls disabling MFA on the target "the best practice". Invicti's manual-intervention mode works only for instant scans, not scheduled ones ([Rapid7](https://docs.rapid7.com/insightappsec/authentication/); [Invicti LSR](https://docs.invicti.com/ip/record-a-login-sequence)). Level Access's Desktop Crawler App handles "multi-factor authentication or biometrics" by having a person sign in through a Chrome window it opens ([Level Access: DCA](https://client.levelaccess.com/hc/en-us/articles/24038696005399-Scan-with-the-Desktop-Crawler-App-for-platform)). Selenium's documentation is the bluntest: "you should avoid automating 2FA" ([Selenium](https://www.selenium.dev/documentation/test_practices/discouraged/two_factor_authentication/)).

The identity providers point the same way.

**Auth0.** A July 2026 Auth0 post says to "Keep Development permissive" because "Your integration tests do not need to pass MFA challenges, but your production users absolutely do" ([Auth0 blog: Single-tenant trap](https://auth0.com/blog/the-single-tenant-trap-why-testing-in-production-kills-uptime/)). Auth0's December 2024 testing article drives the real Universal Login and contrasts it with the "deprecated OAuth 2.0 Password Grant" ([Auth0 blog: Cypress](https://auth0.com/blog/testing-auth0-login-with-cypress/)). Its Resource Owner Password docs say plainly "we do not recommend it", and with MFA on, that grant returns `mfa_required` ([Auth0: ROPG](https://auth0.com/docs/get-started/authentication-and-authorization-flow/resource-owner-password-flow); [Auth0: ROPG with MFA](https://auth0.com/docs/secure/multi-factor-authentication/authenticate-using-ropg-flow-with-mfa)).

**Microsoft.** Microsoft's integration-testing guide still describes the password grant (ROPC), but only "in a separate test tenant, and only with test users", with those users and apps excluded from MFA Conditional Access ([Microsoft Learn: Automated integration tests](https://learn.microsoft.com/en-us/entra/identity-platform/test-automate-integration-testing)). It has also deprecated ROPC across MSAL.NET, msal-node, msal4j, MSAL Python, MSAL Go and Azure Identity, and calls it "incompatible with MFA" ([Microsoft Learn: Mandatory MFA](https://learn.microsoft.com/en-us/entra/identity/authentication/concept-mandatory-multifactor-authentication)).

**Clerk, Firebase and Google.** Clerk ships the only true testing mode. Its Testing Tokens "bypass bot detection mechanisms", and its server-side sign-in token "bypasses all verification steps, including … multi-factor authentication" ([Clerk: Testing overview](https://clerk.com/docs/testing/overview); [Clerk: Playwright helpers](https://clerk.com/docs/testing/playwright/test-helpers)). Firebase offers fixed-code test phone numbers and an emulator that disables reCAPTCHA ([Firebase: Phone auth](https://firebase.google.com/docs/auth/web/phone-auth); [Firebase: Auth Emulator](https://firebase.google.com/docs/emulator-suite/connect_auth)). Google consumer accounts restrict sign-in from browsers "controlled through software automation" ([Google Account Help](https://support.google.com/accounts/answer/7675428)).

TOTP itself constrains how a tool may behave. RFC 6238 says the verifier "MUST NOT accept the second attempt of the OTP after the successful validation has been issued for the first OTP". **Two logins in one 30-second window with the same seed will therefore collide** ([RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)). Failed-attempt limits are tight. Auth0 allows **ten wrong OTPs, then imposes a wait of at least six minutes** ([Auth0 Support: MFA limits](https://support.auth0.com/center/s/article/MFA-limits-for-OTP-and-SMS-failed-input)). Okta allows **five failures in a rolling five minutes** and tolerates up to two minutes of clock skew ([Okta: Google Authenticator](https://help.okta.com/oie/en-us/content/topics/identity-engine/authenticators/google-authenticator.htm)). Cognito accepts codes only within 30 seconds either way and only from SHA1 ([AWS: TOTP](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-mfa-totp.html)).

Getting the seed is easiest on Auth0. `POST /mfa/associate` returns the base32 `secret` and a ready-made `otpauth://` URI declaring SHA1, 6 digits and period 30, along with recovery codes ([Auth0: Enroll OTP](https://auth0.com/docs/secure/multi-factor-authentication/authenticate-using-ropg-flow-with-mfa/enroll-and-challenge-otp-authenticators)). Okta exposes `sharedSecret` at enrollment ([Okta: Google Authenticator guide](https://developer.okta.com/docs/guides/authenticators-google-authenticator/nodeexpress/main/)), and Cognito returns the seed from `AssociateSoftwareToken` ([AWS: TOTP](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-mfa-totp.html)). The generic route is the "Can't scan the QR code" option at enrollment ([New Relic](https://github.com/newrelic/quickstarts-synthetics-library/blob/main/library/2FAOrMFA/config.yml)).

Lockout controls are aimed at exactly the traffic a scanner generates: repeated logins of one test user from datacenter IPs. **Auth0 brute-force protection** blocks an identifier after **10 failed attempts from one IP, for up to 30 days** ([Auth0: Brute-force protection](https://auth0.com/docs/secure/attack-protection/brute-force-protection)). Auth0's suspicious-IP throttling applies a daily per-IP failed-login threshold, which a support article gives as 100 login attempts per day by default ([Auth0: Suspicious IP throttling](https://auth0.com/docs/secure/attack-protection/suspicious-ip-throttling); [Auth0 Support: Defaults](https://support.auth0.com/center/s/article/Default-values-for-Suspicious-IP-Throttling), search excerpt). Entra smart lockout trips after 10 failures, and separately blocks anomalous IPs with `AADSTS50053` "regardless of the password validity" ([Microsoft Learn: Smart lockout](https://learn.microsoft.com/en-us/entra/identity/authentication/howto-password-smart-lockout)). Okta ThreatInsight rate-limits or blocks suspicious IPs unless they sit in an Exempt Zone ([Okta: ThreatInsight](https://help.okta.com/en-us/content/topics/security/threat-insight/configure-threatinsight.htm)). Cypress warns that logging in before every test "can lead to API rate limiting" ([Cypress: Azure AD](https://docs.cypress.io/app/guides/authentication-testing/azure-active-directory-authentication)). Burp warns that repeated scan logins get flagged "as suspicious" and recommends a test instance "with these checks disabled" ([Burp: Best practice](https://portswigger.net/burp/documentation/scanner/authenticated-scanning/recorded-login-best-practice)). Each Auth0 control has its own IP AllowList, and Bot Detection's takes up to 100 entries ([Auth0: Bot Detection](https://auth0.com/docs/secure/attack-protection/bot-detection)).

## What a11ign should build: a verified sign-in loop with explicit escape hatches

The evidence supports keeping a11ign's two structural choices: locating controls by accessible name in a closed vocabulary, and running the login in the same browser as the scan. Around them, a11ign should build a layered system in which the easiest layer handles the common Auth0 case with no steps at all.

### Five layers, ordered by how little the adopter writes

| Layer | What the adopter writes | What it covers | Closest precedent |
|---|---|---|---|
| 1. `login:` block | Start URL, names of three secret env vars, one signed-in check | Combined and identifier-first forms, a round trip through a hosted IdP, TOTP, skippable nudges | ZAP Browser Based Auth with TOTP; Escape `browser_agent` |
| 2. Provider knowledge (built in) | Nothing; optionally `organization:` or `consent:` | Auth0 Universal Login screens by name; later Entra and Okta | ZAP's Microsoft login handling |
| 3. Flows override | Steps in the closed vocabulary, now with `when`, `optional` and `auto` | Custom or ACUL pages, extra fields, tenant-specific screens | ZAP steps with `AUTO_STEPS`, GitLab before/after actions, Datadog optional steps |
| 4. Bring-your-own session | An `--auth-state` file (now multi-origin) from a capture mode or a Playwright setup project | Push or SMS MFA, CAPTCHA that cannot be allowlisted, Google consumer accounts | Playwright `storageState`, Level Access Desktop Crawler App, Lighthouse `chrome-debug` |
| 5. In-suite (later) | A call inside their Playwright tests | Teams with mature login fixtures | Deque axe Watcher, Evinced SDKs |

### The default config is credentials, a seed and a signed-in check

Layer 1 should look like the zero-config rung that ZAP, Invicti, Rapid7 and Escape converged on. To that it adds the TOTP field set ZAP and Burp standardised, and the success check every vendor requires. The syntax below is a proposal, to be adapted to a11ign's actual config grammar.

```yaml
# .a11ign/login.yml   (proposed)
login:
  start: https://staging.example.com/            # any page that sends a signed-out user to sign in
  username: { env: A11IGN_LOGIN_USER }
  password: { env: A11IGN_LOGIN_PASSWORD }
  totp:     { env: A11IGN_LOGIN_TOTP }           # optional: base32 seed OR full otpauth:// URI
  signed-in:
    element: { role: button, name: "Account menu" }   # or: url: https://staging.example.com/app/**
  idp-origins: [https://example-staging.us.auth0.com] # `a11ign login --check` prints this line for you
```

```yaml
# GitHub Actions step   (proposed)
- uses: a11ign/action@v1
  with:
    login: .a11ign/login.yml
  env:
    A11IGN_LOGIN_USER:     ${{ secrets.A11IGN_LOGIN_USER }}
    A11IGN_LOGIN_PASSWORD: ${{ secrets.A11IGN_LOGIN_PASSWORD }}
    A11IGN_LOGIN_TOTP:     ${{ secrets.A11IGN_LOGIN_TOTP }}
```

Three details matter more than the syntax.

**The `totp` value should accept either a bare base32 seed or a full `otpauth://` URI.** Auth0 returns the URI verbatim, and QA.tech takes it whole. When given a URI, a11ign should read `algorithm`, `digits` and `period` from it. Otherwise it should default to SHA1, 6 and 30, the parameters GitLab, Cognito and Auth0's URI assume. Okta's Custom TOTP and Entra hardware tokens can use SHA-256 or 60-second periods, so the overrides must exist even though most adopters will never touch them ([Okta: Custom TOTP](https://help.okta.com/en-us/content/topics/security/mfa-totp-seed.htm); [Microsoft Learn: OATH](https://learn.microsoft.com/en-us/entra/identity/authentication/concept-authentication-oath-tokens)).

**Credentials are referenced by env-var name, never inlined.** Checkly's rule is "Never, ever store credentials in your tests" ([Checkly](https://www.checklyhq.com/docs/learn/playwright/authentication/)).

**`idp-origins` should stay explicit, but a11ign should write it for the adopter.** a11ign's origin pinning is a real safety property: it never types a password into an origin nobody approved. Burp shows the convenient alternative of following the login wherever it goes ([Burp](https://portswigger.net/burp/documentation/scanner/authenticated-scanning/recorded-login-sequences)). The right compromise is for `login --check` to observe the redirect chain and print the exact line to paste. Whether well-known hosted domains such as `*.auth0.com` should be trusted automatically is a judgement call that no evidence settles.

An intermediate override belongs between Layer 1 and full flows. A `fields:` map of accessible names, for example `fields: { username: "Work email", submit: "Sign in to Acme" }`, would cover the localisation and customised-text cases that break name heuristics. It has the same shape as GitLab's and Level Access's field selectors, but uses names instead of CSS. mabl's auto-login fails on non-English pages, and Auth0 lets tenants rewrite every text element, so this escape valve will be needed early ([mabl](https://help.mabl.com/hc/en-us/articles/19078187773972-Auto-login-flows); [Auth0: Customize text elements](https://auth0.com/docs/customize/login-pages/universal-login/customize-text-elements)).

### The engine recognises screens from a catalogue instead of replaying a script

Behind the `login:` block, a11ign should run a loop. After the start page settles, and after each submit, it waits until exactly one known screen or the signed-in check matches, acts, and repeats, all within one overall time budget. This replaces per-step timeouts. Datadog's optional steps each cost up to 60 seconds when their screen is absent. A "wait for any of these states" loop pays nothing for screens that never appear.

Detection should use what a11ign already reads: the accessibility tree, plus field types and `autocomplete` tokens such as `username`, `current-password` and `one-time-code`. That is the right fit for a page whose CSS classes Auth0 rotates on every build and whose accessible markup became the only option in 2025. Auth0's documented prompt and screen names should be the vocabulary for logs and errors, even where a11ign cannot detect them directly, because "stopped at `mfa-otp-enrollment-qr`" tells an adopter exactly what to fix. This research did not establish which signals Universal Login exposes reliably (URL path, headings or field names). They should be confirmed against a live tenant.

| Screen met | Default action | Why, and evidence |
|---|---|---|
| Identifier only (email or username, then Continue) | Type the username, submit | Auth0 Identifier First, Okta any-factor, Entra ([Auth0](https://auth0.com/docs/authenticate/login/auth0-universal-login/identifier-first); [Okta](https://developer.okta.com/docs/concepts/oie-idfirst-signin/)) |
| Password only, or identifier and password together | Type what is shown, submit | Same documents; Burp and ZAP both handle the split |
| One-time-code challenge | Type a fresh TOTP if a seed is configured; else fail `mfa-required-no-seed` | The universal TOTP field set; generate the code immediately before typing ([New Relic](https://github.com/newrelic/quickstarts-synthetics-library/blob/main/library/2FAOrMFA/config.yml)) |
| Factor picker or "Try another method" | Choose the authenticator-app option if a seed is configured; else fail | Auth0 `challengeWithAny` and `additionalFactors` ([Auth0](https://auth0.com/docs/secure/multi-factor-authentication/customize-mfa/customize-mfa-selection-universal-login)) |
| Passkey or authenticator enrollment nudge | Choose the skip or "later" option; record that it happened | Auth0 Progressive Enrollment is on by default; Entra "Skip for now"; Okta optional enrollment |
| "Stay signed in?" or keep-me-signed-in | Answer No by default (configurable); never leave it unanswered | Entra logs 50140 when the prompt is abandoned ([Microsoft Learn](https://learn.microsoft.com/en-us/entra/fundamentals/how-to-manage-stay-signed-in-prompt)) |
| Consent or login confirmation | Accept and warn with the tenant fix; `consent: fail` for strict adopters | ZAP accepts Microsoft's consent screen automatically ([ZAP changelog](https://www.zaproxy.org/docs/addons/authhelper/changelog/)); `localhost` callbacks always trigger it in Auth0 |
| Organization picker | Choose `organization:` if set; else fail, listing the options seen | Auth0 Organizations flows |
| MFA enrollment required (QR code or factor list) | Fail `mfa-enrollment-required`: the test user has no authenticator enrolled | Not skippable, and enrolling a factor automatically would silently change the account |
| CAPTCHA or bot challenge | Fail `bot-challenge` with the AllowList fix; never attempt to solve it | Burp: CAPTCHAs "are specifically designed to deny automated systems" ([Burp](https://portswigger.net/burp/documentation/scanner/authenticated-scanning/recorded-login-best-practice)) |
| Brute-force block, or wrong-credential error | Fail immediately, no retry | Auth0 blocks for 30 days; Entra lockouts escalate |
| Nothing recognised within the budget | Fail `unknown-screen` with the artifact and a suggested flows step | ZAP fails deliberately "if not able to perform all the expected steps" |

Cypress's objection to conditional logic is fair, and the mitigation is visibility. Every branch the loop takes should appear in the run summary, for example "skipped passkey enrollment nudge (Auth0 Progressive Enrollment is on for this connection)". That keeps runtime tolerance from hiding tenant drift.

The suggested-step idea suits a11ign unusually well. When the loop meets an unknown screen, it already holds that screen's accessibility tree, so it can print the exact flows step it would need, such as `press: { button: "Remind me later" }, optional: true`. Burp built its December 2025 step editor for the same reason: "Login flows change, and when they do, authenticated scans often break" ([PortSwigger blog](https://portswigger.net/blog/burp-suite-dast-winter-update-2025)).

### Prove sign-in before the scan and on every page

ZAP's zero-config failures were mostly verification failures, so verification deserves the most care.

The signed-in check should validate itself. a11ign should evaluate it on the signed-out start page before logging in, and refuse a check that already matches there. Burp raises an error when "the confirmation text … appears while unauthenticated", and Pope Tech's success identifier "must not be present on the login URL" ([Burp: Error reference](https://portswigger.net/burp/documentation/scanner/burp-scanner-error-reference); [Pope Tech](https://app.pope.tech/help-center/article/configure-website-authentication)). After logging in, a11ign should wait for the final URL as well as the element, because a login "sets cookies in the process of several redirects" ([Playwright: Authentication](https://playwright.dev/docs/auth)).

When the adopter supplies no check, a11ign should fall back to "back on the app origin, with no password field and no IdP origin present". That mirrors GitLab's default `DAST_AUTH_SUCCESS_IF_NO_LOGIN_FORM` ([GitLab DAST](https://docs.gitlab.com/user/application_security/dast/browser/configuration/authentication/)). It should also print a warning recommending an explicit element. Level Access's advice applies directly: choose an element that appears "on every page after login and that's visible without user interaction", such as a log-out button ([Level Access](https://client.levelaccess.com/hc/en-us/articles/5324907203863-Set-up-secure-web-authentication)).

The same check should then run before each scanned page is audited. It is cheap, and it is the only defence against the failure escape.tech describes, in which a scanner "falls back to crawling as an anonymous visitor, and still finishes green" ([escape.tech](https://escape.tech/blog/authenticated-scanning-oauth-mfa-captcha/)). If the check fails, a11ign should re-run the login once. If it still fails, the page should be reported as "not audited: signed out", never as an audit of the login page. Rapid7 and StackHawk both re-authenticate when they detect a logout, and StackHawk raises a coverage warning when more than 5% of requests are unauthenticated ([StackHawk](https://docs.stackhawk.com/hawkscan/authenticated-scanning/)). a11ign should apply an equivalent run-level gate.

A page that fails the check only after a hard navigation needs its own diagnosis, `session-not-restorable-on-navigation`. It means the SPA cannot restore a memory-only session on reload. The remedies are refresh tokens or a localStorage cache in the test build ([Auth0: SPA SDK](https://auth0.com/docs/libraries/auth0-single-page-app-sdk)), or in-app navigation steps in the flow.

Level Access fails any scan that includes the login page ([Level Access](https://client.levelaccess.com/hc/en-us/articles/5324907203863-Set-up-secure-web-authentication)). a11ign should likewise warn when a scan target is the login URL or sits on an IdP origin.

For a CI gate, **a lost session should fail the run, the opposite of Burp's choice**. A failed Burp login replay "won't cause the scan to fail completely" (search excerpt; [Burp: Error reference](https://portswigger.net/burp/documentation/scanner/burp-scanner-error-reference)). That default suits an exploratory security scan but is wrong for an accessibility gate whose green check people trust. Login failure should get its own exit code, distinct from "violations found".

### Flows remain the override, with optional and conditional steps

Hand-written flows remain right for ACUL tenants, custom login pages and anything the catalogue does not know. They need four additions. A `when:` condition runs a step only if its target is present once the page settles, with no timeout cost, and `optional: true` tolerates a missing target. An `auto: true` step hands control back to the built-in loop, the equivalent of ZAP's `AUTO_STEPS` ([ZAP: Browser Based Authentication](https://www.zaproxy.org/docs/desktop/addons/authentication-helper/browser-auth/)). A `dismiss-if-shown:` list gives Playwright-style handlers for interstitials that can appear at any point ([Playwright: addLocatorHandler](https://playwright.dev/docs/api/class-page#page-add-locator-handler)).

The example below is illustrative and must be mapped onto the real flows grammar.

```yaml
# flows override for a customised login page   (proposed additions marked "new")
login:
  origin: https://staging.example.com
  idp-origins: [https://login.example.com]
  dismiss-if-shown:                                   # new: checked before every step
    - { button: "Accept all cookies" }
  steps:
    - type:  { into: "Work email", text: { env: A11IGN_LOGIN_USER } }
    - press: { button: "Continue" }
    - press: { button: "Use password instead" }
      when:  { button: "Use password instead" }       # new: only if present
    - type:  { into: "Password", text: { env: A11IGN_LOGIN_PASSWORD } }
    - press: { button: "Sign in" }
    - auto: true                                      # new: built-in loop handles TOTP, nudges, KMSI
  signed-in:
    element: { role: link, name: "Sign out" }
```

### Bring-your-own session covers the MFA the loop cannot answer

`--auth-state` should carry cookies for the declared IdP origins as well as the app's own origin, so that silent re-authentication has the IdP session cookie it needs. It should also carry sessionStorage, which Playwright omits; Playwright's docs give the save-and-restore workaround ([Playwright: Authentication](https://playwright.dev/docs/auth)). a11ign should keep reading plain Playwright `storageState` files unchanged, so the output of a team's existing setup project still works. That is Deque's documented integration, and the cheapest form of "in-suite" support ([axe Watcher](https://docs.deque.com/devtools-for-web/4/en/wa-storagestate/)).

To produce the file, a11ign should add a person-present capture mode, `a11ign login --capture`. It opens Edge on the adopter's machine, waits for them to sign in with any factor, verifies the signed-in check, and writes the state. The same pattern sits behind Level Access's Desktop Crawler App, Lighthouse's `chrome-debug` and Playwright's `codegen --save-storage` ([Level Access](https://client.levelaccess.com/hc/en-us/articles/24038696005399-Scan-with-the-Desktop-Crawler-App-for-platform); [Lighthouse](https://github.com/GoogleChrome/lighthouse/blob/main/docs/authenticated-pages.md); [Playwright codegen](https://playwright.dev/docs/codegen)). Adopters should be told plainly that captured state expires and that refresh-token rotation can invalidate it ([#32594](https://github.com/microsoft/playwright/issues/32594)). That makes capture the right tool for push or SMS MFA and for local runs, and the wrong default for unattended CI. a11ign should treat the file as a credential, following Playwright's warning to "only use the auth.json locally as it contains sensitive information".

A full in-suite mode should wait. Deque's need for `mergeTests` shows the composition friction ([axe Watcher](https://docs.deque.com/devtools-for-web/4/en/wa-storagestate/)), and a state file already captures most of the value. A recorder should come last. Recordings break when the UI changes: that is Detectify's main failure cause and the reason Burp built a step editor ([Detectify](https://support.detectify.com/support/solutions/articles/48001049282-scan-behind-login-with-recorded-login)). For Auth0, the screen loop plus suggested steps does the recorder's job without leaving a stored artefact to rot. If a recorder is ever built, capture mode can emit the accessible-name steps it observed.

### Failure reports name the screen and the fix

a11ign should ship `a11ign login --check`, which runs only the login and the verification, locally or in CI. Every serious tool has an equivalent: ZAP's Authentication Tester, Burp's pre-scan check, Pope Tech's "Test Authentication", BrowserStack's "Verify login configuration" and UserWay's "Test This Journey" ([ZAP: Auth tester results](https://www.zaproxy.org/docs/authentication/auth-tester-results/); [Burp: Pre-scan check](https://portswigger.net/burp/documentation/dast/user-guide/scanning-web-apps/pre-scan-check)).

The failure artifact should meet the bar ZAP and GitLab set: per-step screenshots, the HTTP trace, and the DOM or storage state ([ZAP blog 2026-02-02](https://www.zaproxy.org/blog/2026-02-02-zap-updates-2025-highlights-2026-plans/); [GitLab DAST](https://docs.gitlab.com/user/application_security/dast/browser/configuration/authentication/)). a11ign should add what only it has: the accessibility tree of each screen, which shows the names the loop saw. Each step should also record its origin, the screen it was classified as, the action taken and the timing. Typed passwords and codes must be redacted and token and cookie values stripped, because GitLab warns that its own report contains credentials. a11ign should also keep only the last failed attempt, as ZAP's newest `auth_on_failure` diagnostics do.

Errors should be named outcomes with one-line remedies, modelled on ZAP's tester outcomes and matched against known provider signatures such as HTTP 429, Auth0's "Too many failed codes", Entra's `AADSTS50053` and 50140, Clerk's "Bot traffic detected" and Cognito's "Request not allowed due to WAF captcha".

| Outcome | Remedy line shown to the adopter |
|---|---|
| `start-page-unreachable`, `no-sign-in-form` | Check `start`; confirm it redirects a signed-out user to sign in |
| `credentials-rejected`, `account-blocked` | Fix the secret; unblock the user in the IdP (no retry was made) |
| `mfa-required-no-seed`, `totp-rejected`, `mfa-enrollment-required` | Add or fix `totp`, sync the worker clock, or enroll the test user once |
| `bot-challenge`, `rate-limited` | Add the runner's egress IP to the IdP's allowlists |
| `consent-required`, `organization-required` | Enable consent skipping, or set `consent:` or `organization:` |
| `unknown-screen` | Paste the suggested flows step, or add a `fields:` override |
| `signed-in-check-never-matched`, `signed-in-check-matches-signed-out` | Choose an element present only when signed in, such as "Sign out" |
| `session-lost-mid-scan`, `session-not-restorable-on-navigation` | Enable refresh tokens in the test build, or use in-app navigation steps |

### Never be the reason a test account gets locked

The lockout figures above translate into a short set of engineering rules. The rules are design judgements, though each follows from the cited limits.

**One login per run.** a11ign should log in once per run and reuse a single browser context for every page, never logging in per page or per URL. This is the Playwright and Cypress pattern, and it avoids the rate limits Cypress warns about.

**No retry after a rejection.** It must never retry after a credential or TOTP rejection. Correct passwords do not count toward Auth0's brute-force counter, so the real danger is a misconfigured secret retried into a 30-day block ([Auth0](https://auth0.com/docs/secure/attack-protection/brute-force-protection)).

**Narrow, capped retries.** The whole login should be retried at most once, only after transient failures such as timeouts or 5xx responses, and only after a backoff. Per-page re-login should be capped at one, under a hard cap on login attempts per run.

**Fresh, non-repeating TOTP codes.** Each code should be generated immediately before it is typed. a11ign should remember which time step it last used within the run, and wait for the next step before any re-login rather than replay a code. RFC 6238 requires this, and Burp's throttle exists for the same reason.

**No shared users across parallel jobs.** Parallel jobs that share a test user will collide on TOTP windows and multiply failure counts. Adopters should use one user per job, following Playwright's "one account per parallel worker", or serialise the jobs. QA.tech's advice is to "Configure provider limits before scaling parallel plans" ([QA.tech](https://docs.qa.tech/best-practices/handle-auth)).

**NTP-synced worker clocks.** The Windows worker's clock must be synced, because Cognito tolerates only ±30 seconds.

**Optional identifying header.** An identifying request header, like Datadog's `x-datadog-origin: synthetics`, lets adopters write WAF rules ([Datadog: Identify bots](https://docs.datadoghq.com/synthetics/guide/identify_synthetics_bots/)). The identity providers' own exemptions are IP-based, though, so the header is a convenience rather than a fix.

### Tell adopters to make the tenant boring

Adopter documentation should open with the consensus every source shares: **a dedicated test user, in a non-production tenant, whose sign-in is deterministic**. Siteimprove asks for a crawler account that "does NOT expire or use a password renewal policy", and Burp suggests screenshotting the QR code when setting up MFA for the scan account ([Siteimprove](https://help.siteimprove.com/support/solutions/articles/80000448387-can-siteimprove-crawl-an-intranet-and-other-non-public-sites-); [Burp DAST: TOTP](https://portswigger.net/burp/documentation/dast/user-guide/scanning-web-apps/configure-authentication/totp-mfa)). Auth0 comes first and its guidance is specific enough to be a checklist. The other providers get one row each.

| Provider | Make MFA deterministic | Let the runner through | Remove interstitials |
|---|---|---|---|
| Auth0 | Use a separate dev/test tenant. Best: skip MFA for the test user with a post-login Action condition ("Customize MFA Factors using Actions"). If MFA must stay, enroll OTP only (via `/mfa/associate` or the "can't scan" code) and store the `otpauth://` URI | Add the runner's egress IP to all three AllowLists: Bot Detection, Brute-force Protection and Suspicious IP Throttling | Turn Passkey Progressive Enrollment off for the test connection; enable "Allow Skipping User Consent" on the API; avoid `localhost` callbacks; use Organizations "No Prompt" or set `organization:` |
| Microsoft Entra | Use a separate test tenant. Exclude the test user and app from MFA Conditional Access, or enroll a software OATH token and store its seed | Avoid repeated failures (smart lockout trips at 10); watch for `AADSTS50053` | Turn off "Show keep user signed in", or let a11ign answer it; exclude the user from registration campaigns (`excludeTargets`) |
| Okta | Apply an enrollment policy where the test user has only an authenticator app enrolled, or a sign-on rule that does not require MFA for that user | Put the runner IP in a ThreatInsight Exempt Zone; check the bot-protection mode | Disable optional authenticators that would prompt enrollment |
| Cognito | Use TOTP via `AssociateSoftwareToken` (SHA1 only) | Add an "Always-allow" IP range in threat protection | Keep the login under the 5-minute prompt timeout |

### Evidence is thinnest on usage, screen order and memory-only tokens

Several recommendations rest on design judgement rather than measurement. No vendor publishes which login tier its customers use or succeed with, and ZAP's 21-target table is the only success data; it is small and partly synthetic. Auth0 does not document the end-to-end order of its screens, for example whether the passkey nudge comes before or after MFA, and it does not promise `username` and `password` field names as a contract. No vendor documents conditional steps for Auth0 or Okta screens. None documents capturing memory-only tokens, and none persists "remember this device" cookies across runs. Whether datacenter IPs raise Auth0 or Okta bot-risk scores is plausible but unconfirmed. mabl's field names and limits came only from search excerpts. The claim that accessible-name detection beats CSS heuristics on hosted login pages is an inference from Auth0's class-rotation warning and its 2025 accessible-UI change, not a measured result. Finally, how memory-only SPAs behave as a11ign navigates from page to page during a scan should be tested on a real Auth0 SPA before the `session-not-restorable-on-navigation` diagnostic is designed in detail.

## Conclusion

The most useful shift in understanding is that a11ign's constraints are advantages here. Auth0 rotates its CSS classes on every build and now serves only accessible Universal Login markup. A tool that finds fields by accessible name is therefore aligned with the most stable signal hosted login pages offer, and a login page that a name-based heuristic cannot read is plausibly an accessibility finding in its own right. Running the login in the same browser that does the scanning is the only approach the evidence supports for SPAs that hold tokens in memory. What a11ign lacks (TOTP, a screen catalogue, verification and diagnostics) is exactly where the industry has invested since 2025, and none of it requires giving up origin pinning or the closed vocabulary.

The opportunity is also larger than parity. No accessibility scanner found automates TOTP or walks a hosted identity provider without scripts written by vendor staff, and several charge extra or open support tickets just to get past a login. An open-source tool that runs in the adopter's own CI with the adopter's own secrets can bring DAST-grade login handling to accessibility teams. The cost should be budgeted honestly: ZAP needed roughly a year of releases to cover one provider's variations. A real Auth0 conformance tenant, built early and run nightly, is the cheapest way to turn that year into weeks. Failing loudly when the session is lost is what will make adopters trust a green accessibility result on authenticated pages.
