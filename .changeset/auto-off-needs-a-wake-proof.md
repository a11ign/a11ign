**Auto-off powers a worker down only while it has proved it comes back, and names the ones that have not (#3227).** The pool's only admission test was `hasWakeableMac`, whose answer is a well-formed MAC, so auto-off removed boxes nobody could restore (worker 4 never appeared on the network after a wake, worker 6 woke at a different address; both read by the chairman's session on 2026-10-03, not re-measured here). `fleet-wake.mjs` now keeps a per-worker proof ledger (`runs/fleet-wake-proof.json`, `provenAt` by worker name): ONLY a wake that began from a silent worker and ended `ready` at the inventory's own address (`woken`) writes one; `already-up`, `busy`, `came-up`, and a worker that answered only elsewhere (which reads `no-answer`) write none, and a wake that fails drops the proof that worker held. `autoOffDecision` takes `wakeProvenAt` and keeps an otherwise-off worker as `wake-unproven` when it has no proof or the proof is older than `PROOF_WINDOW_MS`, a rank above `idle-five-minutes`; the CLI prints the unproven workers by name with the remedy, and the wake report says whether each outcome proved or dropped. The window is 7 days, with the derivation beside it: the recurring unobserved change (a Windows servicing update resetting the NIC) is monthly, which is a ceiling under 31 days, and a week below it is a judgment, because lapsing early costs a box left on while lapsing late costs a box that cannot be restored. A missing or corrupt ledger reads as no proof for anyone. **Until a worker has been through `fleet:sleep` then `fleet:wake` nothing is powered off**, which is the safe direction; every `wakeFleet` caller that really sends (the lab's `lab-job` wake included) records its own proof on the host it runs on.
