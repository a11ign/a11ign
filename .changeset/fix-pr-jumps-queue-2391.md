**`arm-pr.mjs` can put the fix for a red `main` at the FRONT of the merge queue (#2391, follow-up to #2356).** A pull request whose body carries a line `Fixes-trunk: <sha>` — the merge `trunk.yml` read red, which the `trunk-red` order names — is enqueued with `enqueuePullRequest(jump: true, expectedHeadOid)` instead of being armed at the back, once `mergeStateStatus` is `CLEAN`. The three decisions the row delegated are pinned as `TRUNK_FIX_POLICY`: the jump is granted only while `main`'s newest `trunk.yml` verdict is red and the marker names a merge in the current red streak (so it survives the merges that land on a red `main`, and ends with the red; the streak is read a page of 100 runs at a time until a green ends it or the marker's merge is found, capped at 10 pages, and a streak that outruns the cap without naming the marker is reported as unreadable rather than as naming nothing); a refused jump still arms the ordinary way, and an unreadable trunk is not a red one; and nothing here ever removes a queued PR, so a second red never displaces a fix already in the queue. **The verdict is `mergeQueueEntry.position` read back, never the mutation's exit code** — a jump that reads back anywhere but position 1 exits `4` (`JUMP_UNCONFIRMED`) and says where the PR is. An unmarked PR costs no extra call. Not yet exercised against the live `merge-queue-main` ruleset: no red trunk exists to do it on, and the PR says how the first reading will be taken. `arm-pr.test.ts`'s #2046 guard is narrowed from the strings `mergeQueueEntry` / `pullRequest(number` to the armed rule's own field `autoMergeRequest`, with the one allowed queue-seat query pinned by name.
