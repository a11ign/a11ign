**A pipeline pull request CODEOWNERS assigns to `ceo` and that `ceo` has not approved now wakes `ceo` (#1959).** `.github/CODEOWNERS` names `@DanBeckDev` (`ceo`) as owner of `/.github/workflows/`, carving out the generated `consumer-gate.yml`, but nothing in `work-gate.mjs`'s fourteen-plus causes ever asked whether that review had happened — measured 2026-09-22, `DanBeckDev` has never authored a formal GitHub review in this repository, and of the last 150 merged PRs, 12 touched `.github/workflows/` with at least three engineer-authored against a path CODEOWNERS does not carve out. The gap is advisory today and becomes a hard merge block the moment #1756 flips `require_code_owner_reviews` on.

The new `pr-codeowner-review-missing` cause (an ACTION cause, FINISH: a drain does not withhold it) reads `docs/lane-ownership.json`'s pipeline lane and, for every open pull request, checks whether it touches a path CODEOWNERS actually assigns to the lane's owner (inside `paths`, outside every `except` entry — the same last-matching-pattern rule GitHub applies) and carries no `APPROVED` review from that owner's GitHub login. It excludes a pull request the owner authored, since GitHub never requests a review from a PR's own author and the bypass allowance #2022 requires covers that case. It rides on `readPrs`'s existing `files`/`reviews` fields and `decide`'s existing `prFiles` (`comparablePrFiles`'s truncation-safe output) — no new `gh` call. One set order wakes `ceo`, naming every pull request still missing the review; a labelled one names its session for context only, since the review is always `ceo`'s to give.
