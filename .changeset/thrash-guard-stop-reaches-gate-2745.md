**A Claude Code thrash-guard stop is now a distinct signal, and it is never answered with the identical order (#2745).** Claude Code's own autocompact "rapid refill breaker" (context refilled to the limit within 3 turns of a compaction, 3 times in a row) ends the turn on its own with an `autocompact_thrashing` message and leaves the pane exactly where any other finished turn leaves it -- `herdr` reports `idle`/`done` either way, so nothing previously told the gate the difference (#2743: worker-2623, 139 compactions, 5.4 hours, to a human's manual interruption, not a code-level stop). `paneThrashed` (`claim-stall.mjs`) reads the message's opening clause off the pane's last paragraph -- past Claude Code's own completion footer, and anchored the same way `paneInterrupted` anchors to the last line, since the message is long enough to wrap across several terminal lines. `recoverableWork`/`recoverInterruptedWork` (`wake.mjs`) now report a thrashed session separately from an interrupted one, sharing the same one-pane-read-per-session cost, and a thrashed session is deliberately **not resumed**: resending "continue where you left off" would very likely refill its context and trip the guard again, which is the defect this exists to stop. `product-manager` gets a `thrashEscalationPrompt` order instead, naming the session and its row and asking for a decision (release the claim for a fresh instance, or an explicit `/clear` first) -- the routing rule's own reader for a report that needs one. Idempotent per thrash episode through the same `resentAt`/`quiet` window the interrupted-pane path already uses.
